How the Three Lessons Connect

A technically correct system can still fail if it solves the wrong problem, arrives too late, costs more than the organization can sustain, cannot be supported, or does not fit the legal and operating conditions of the places where it will be used. Keep the whole topic organized by asking three questions in sequence:

1. Building Information Systems

What should be built, how should it be designed, and how do we decide it is ready to use?

2. Managing Projects

How do we control scope, schedule, cost, risk, quality, and responsibility while the system is delivered?

3. Managing Global Systems

What changes when the same system must serve users, laws, languages, currencies, networks, and support teams across countries?

Final Recommendation

Never "just pick a technology." State the business requirement, delivery approach, project controls, operating model, major risks, evidence required before release, and the conditions that could change the recommendation.

Assessment Questions to Always Ask

  • Building: Are we building the right system in a way that can be operated and supported?
  • Managing: Do we have credible control over delivery, and can problems be seen early enough to act?
  • Global: Can the system operate consistently across locations without ignoring legitimate local requirements?

Lesson 1 — Building Information Systems

What "Building a System" Actually Includes

An information system is not only software — it includes people, procedures, data, controls, and technology organized to support work and decisions. A programmer can build a form quickly; that alone doesn't mean the organization built a good information system.

Business Need→ Analysis→ Design→ Build / Configure→ Test→ Convert→ Operate & Improve↻

Levels of Organizational Change

  1. Automation — the same task, done automatically.
  2. Process rationalization — simplify duplicate steps or rework.
  3. Business-process redesign — change order/ownership/structure of work.
  4. Change to the operating model — the largest change, affecting budgets, ownership, and governance.

Systems Analysis vs. Systems Design

Analysis defines the problem and requirements before committing to a solution. Design decides how the requirements will be satisfied. Confusing the two creates expensive rework — e.g., jumping straight to "we need a mobile app" is a design choice, when the real requirement might just be "reserve from any device."

Functional "The system must prevent two active reservations for the same item and time."

Non-functional "Search results should appear within 2 seconds for normal load."

Requirements need priority: MustShouldCould / not planned. Ask: "Would we cancel the release if this were missing?" If no — it's probably not a true Must.

The Four Feasibility Checks

TypeKey Question
TechnicalCan we acquire/support the technology and skills required?
EconomicDo benefits justify the complete cost (license, training, support, infra)?
OperationalWill it actually work with real users and policies?
ScheduleCan it be delivered in the required time?

A high overall feasibility score should never hide an unresolved mandatory requirement — a strong average does not equal "approved."

Testing & Conversion

Unit → Integration → System → UAT — each test should trace back to a requirement. Conversion patterns:

  • Direct changeover — fast, high risk
  • Parallel operation — safer, more workload
  • Pilot conversion — one group/location first
  • Phased conversion — staged rollout
Real-life example: Campus Equipment Booking

Release capacity = 21 effort points. Must requirements (sign-in 3, search 5, reserve 8 = 16 points) are protected first; "Could" items like the usage dashboard are deferred. Feasibility scored 4.10/5 overall — but schedule feasibility (3/5) was the weakest area, so scope had to stay controlled even though the average looked strong.

Lesson 2 — Managing Projects

Scope & the WBS

Scope is not a feature list — it states outcome, deliverables, boundaries, assumptions, and exclusions. A Work Breakdown Structure (WBS) decomposes the result into estimable, assignable work packages — including non-programming work like training, UAT, and closeout.

Critical Path Logic

The critical path is the longest dependency path through the project network — it sets the earliest possible finish. Example:

TaskDescriptionPredecessorDuration
AConfirm requirements—2 days
BDesign screensA3 days
CBuild databaseA4 days
DIntegrate portalB and C3 days
EUATD2 days

Path A-C-D-E = 2+4+3+2 = 11 days (critical). Path A-B-D-E = 10 days (has 1 day of float). B can slip 1 day without changing the finish date — C cannot.

Earned Value Management

PVPlanned Value — budgeted value of work that should be done
EVEarned Value — budgeted value of work actually done
ACActual Cost — what was actually spent
FormulaExampleMeaning
SV = EV − PV7,600 − 10,000 = −2,400Behind planned progress
CV = EV − AC7,600 − 8,600 = −1,000Spent more than value earned
SPI = EV ÷ PV0.76<1.00 → behind schedule
CPI = EV ÷ AC0.88<1.00 → over budget for work achieved

These indexes tell management WHERE to investigate — not automatically WHY. Root causes still need diagnosis.

Risk vs. Issue

A risk is uncertain and hasn't happened yet; an issue has already happened. Good risk statements include cause → event → effect, not just a label like "database delay." Responses: avoid, reduce, transfer, accept.

RACI & Change Control

RACI = Responsible (does the work), Accountable (owns the decision), Consulted (gives input), Informed (kept updated). A task should not have two people believing they're the final Accountable decision-maker.

Even a reasonable change request (e.g., "add QR code check-in") needs impact analysis — requirements, design, test cases, security, schedule, cost — before it's approved, rejected, or deferred.

Lesson 3 — Managing Global Systems

Standardization vs. Local Responsiveness

Organizations usually want both: standardization (shared processes, data, security, software) and local responsiveness (laws, language, payments, support hours). The task is deciding what to standardize vs. what to localize — never "standardize everything" or "let every region choose."

Business Strategy → System Configuration

StrategyTypical System
Domestic exporterCentralized
MultinationalDecentralized (local autonomy)
FranchiserDuplicated core + local extensions
TransnationalNetworked (global core + regional services)

Four System Configurations

  • Centralized — simplifies standards; risks central dependency
  • Duplicated — common core copied per region; version control is the challenge
  • Decentralized — max local autonomy; duplicate work, inconsistent data
  • Networked — shared global core + regional services; strongest governance needed

Global Core vs. Controlled Local Variation

Global Core

Identity standards, master data, security baseline, core transaction rules, shared reporting, integration interfaces.

Local Variation

Language, currency display, local tax logic, invoice fields, payment methods, support schedules, regulatory notices.

Review question: "What would break if this were standardized?" If only "user habit" — standardize it. If "a legal requirement would be violated" — localize it.

Privacy, Language, Time Zones

  • Privacy: map data flows (logs, backups, analytics, support tools) — not just server location.
  • Language: localization ≠ translation — formats, character sets, legal wording, accessibility all differ.
  • Time zones: store timestamps in UTC; convert for display. "Follow-the-sun" support needs disciplined handoffs.
Real-life example: Global Tutoring Platform Rollout
RegionWeighted ReadinessSupport Overlap (13:00–21:00 UTC window)
Canada-East4.85 / 5 — ReadyStrong overlap
Spain3.70 / 5 — Needs workLimited overlap
Singapore3.50 / 5 — Needs workNo overlap

Even a high readiness score can't override a missing mandatory legal, financial, or support gate.
